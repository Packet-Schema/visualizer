# Git ワークフロー

Git 操作が必要な場合は、ユーザーや他作業者の変更を壊さないことを最優先にする。

## 事前確認

1. `git status` や `git diff` で既存差分を確認する。
2. 自分の作業と無関係な差分は戻さず、そのまま扱う。
3. 自分の作業対象と衝突しそうな差分がある場合は、作業を止めてユーザーに確認する。
4. 検証が必要な変更では、整形やビルドを含む確認方針を `verify-change` に従って先に整理する。

## ブランチ

新しくブランチを切る場合は、内容に応じて次の形式を目安にする。

- `feat/<short-slug>`
- `fix/<short-slug>`
- `docs/<short-slug>`
- `refactor/<short-slug>`
- `test/<short-slug>`
- `chore/<short-slug>`

## リモート更新の取り込み

ブランチ作成前、作業再開時、コミット後からプッシュ前、PR 作成前など、リモートとの差分が問題になりやすいタイミングでは、必要に応じて main など作業ブランチの元になったブランチの最新状態を確認する。

1. まず `git status` で未コミット差分を確認する。
2. `git fetch origin` でリモートの最新状態を取得する。
3. 現在の作業ブランチがどのブランチから作られたかを確認し、通常は `origin/main` などを基準にする。
4. 未コミット差分がない、または安全に一時退避できる場合に限り、`origin/main` などの更新を現在の作業ブランチへ取り込む。
5. 取り込みで競合した場合は、勝手に大きな解決をせず、競合箇所と選択肢を整理してユーザーに確認する。

取り込み方法は、既存履歴を不必要に書き換えないことを優先する。ユーザーから明示がない場合は、チームの履歴方針が読み取れるときはそれに従い、判断できない場合は `git merge origin/main` のように merge で取り込む。rebase が明示されている運用では `git rebase origin/main` を使ってもよいが、すでにプッシュ済みのブランチや他者も使っているブランチでは特に慎重に扱う。

merge や rebase、競合解消によって差分や生成物、実行結果に変化が入りうるため、取り込み後は自分の変更でなくても検証が必要な変更として扱い、`verify-change` に沿って必要な確認を行う。

## コミット

コミットメッセージに厳密な規約はない。変更内容が読みやすく伝わる短い要約を優先する。
コミットメッセージの内容は、ユーザーから明示的な指定がない限り、必ず `git diff` の差分内容をもとに考える。

コミット前には、次を確認する。

- `git status` と `git diff` で、意図しないファイルや無関係な差分が含まれていないこと。
- 検証方針は `verify-change` を参照し、変更内容に応じて `run-format`、`run-lint`、`run-test`、`run-typecheck`、`run-build`、`run-build-presets` を使うこと。
- `run-format` を一度通したあとにテスト、Lint、ビルド、preset 生成などでファイル内容が変わった場合は、コミット直前にもう一度 `npm run format:check` が通ることを確認すること。
- 検証後に差分が変わった場合は、`git status` と `git diff` で意図しない変更が混ざっていないこと。
- `.gitignore` 対象の生成物を検証のために更新した場合は、コミット対象に含める意図があるかを `git status`、`git add`、`git diff --cached` の各段階で確認すること。明示的な理由がない限り `git add -f` は避ける。
- 未実施の検証がある場合は、理由を整理してユーザーに共有できること。

ステージング後は `git diff --cached` で、コミット対象の差分が意図どおりであることを確認する。

## プッシュ

プッシュ前には、最後に確認した差分・履歴・検証結果から状況が変わっていないかを確認する。

コミット前など、プッシュ以前の段階で必要な検証を済ませていて、その後に追加の差分、merge や rebase による履歴変更、リモート更新の取り込み、生成物更新がない場合は、同じ検証をプッシュ前に繰り返さなくてよい。ただし `npm run format:check` だけは、最後にファイル内容が変わった時点より後で通過済みであることを必ず確認する。

次のいずれかに当てはまる場合は、変更内容に応じて改めて確認する。

- プッシュ対象のコミットや取り込み済みの変更をまだ確認していない。
- コミット後に差分、生成物、設定、依存関係が変わった。
- merge や rebase、リモート更新の取り込みで履歴や内容が変わった。
- 検証結果が古くなった可能性がある。
- 未実施の検証が残っている。

改めて確認する場合は、基本的にコミット前確認と同じ観点で見直す。特に、`git status` と `git diff` による差分確認、`verify-change` に沿った必要な検証の実施状況、未実施検証の有無を確認する。
プッシュ前の最終確認では、`git diff --cached` または `git show --stat --oneline -1` も使って、直前のコミットに ignore 対象の生成物や意図しない整形差分が混ざっていないことを確認する。

未実施の検証が残っている場合は、理由を整理してユーザーに共有する。

## PR 準備

PR を作る前提の変更では、次を説明できる状態に整理する。

- 関連 issue
- 変更点
- テスト方法や確認結果
- 未実施の検証がある場合の理由

PR 準備時も、整形を含む必要な検証が `verify-change` に沿って完了している前提で整理する。

PR を作成するときは `.github/PULL_REQUEST_TEMPLATE.md` を参照し、記載項目に沿って内容を整理する。
